CC+: AI summaries of customer feedback

A feedback platform for a B2B construction-supply company in Singapore. It collects WhatsApp and form feedback, classifies it, and writes a weekly digest for account managers.

  • ProblemCustomer feedback lived in WhatsApp threads and people's heads, so problems went unnoticed until they cost a project.
  • ApproachClassify each message, then summarise the week per aspect with Claude, grounded in the classification signals.
  • ResultDeployed and handed over to the industry partner in April 2026. Cached weekly summaries load in under 5 seconds.
  • My roleOwned the summariser from research to production, set up CI/CD, and wrote all 13 handover documents.
Under NDA, so no public code

The problem

Most of the company's revenue comes from repeat orders, but feedback arrived through WhatsApp and phone calls and lived in individual employees' heads. Each account manager looked after dozens of customers, so problems could go unnoticed until they cost a project. The goal was to collect feedback in one place, make it measurable, and surface what needs action.

How the system works

Feedback arrives from WhatsApp, online forms and on-site visits. A classification engine, built by my AI teammate, tags each message by aspect (product, service, delivery or payment), sentiment, and whether it needs action. Every week my summariser turns that feedback into a short digest for each aspect, shown on a web dashboard and an Android app.

The summariser

  1. Fetch the week's messages along with their classification results.
  2. Hand them to a Python worker, which computes signals for each aspect: message count, average sentiment and overall label.
  3. Send the signals and raw messages to Claude with a fixed, structured prompt (temperature 0) that requires five sections.
  4. Parse the response, store it in PostgreSQL, and serve the cached copy on page load.
  • Process isolation. The Node.js backend runs the Python worker as a separate process, so several hundred MB of model weights never sit in the web server and a model crash can't take the API down.
  • Caching and fallback. A scheduled job writes each week's summary once. Pages load the stored copy in under 5 seconds without calling the model. If the current week has no feedback, the dashboard shows the last non-empty week, clearly labelled as older.
  • Production fixes. Real usage exposed database connection-pool exhaustion under concurrent requests, and an empty-week check that counted messages instead of content. I fixed both and added an admin-only regenerate button.
  • CI/CD and handover. Cloud Build runs tests on every pull request and deploys on merge. I wrote all 13 handover documents, organised with the Diátaxis framework (tutorials, how-to guides, reference and explanation), including 22 tracked tech-debt items.

Alternatives considered

The summariser went through three stages, each driven by how the previous one failed:

  1. Extractive and abstractive models (BART, PEGASUS, FLAN-T5). Extraction produced disconnected fragments, BART and PEGASUS wrote in an overly formal register for construction-site feedback, and FLAN-T5 didn't hold the structure.
  2. GPT-4o-mini vs Claude. Claude scored higher on faithfulness and coverage, judged independently by GPT-4o and Gemini 1.5 Pro, and offered better quality for the cost at projected scale.
  3. Structured prompt plus classification signals. Passing the per-aspect numbers alongside the raw text gave the strongest results on every dimension, and is what shipped.

The jump from an unstructured prompt to a structured, signal-grounded one was bigger than the difference between the two models.

Limitations

  • I designed an 8-condition benchmark with ablations that isolate the prompt and the signals, but only verified it on the first batch before handover. The production choice rests on the staged comparison above, not on a completed statistical benchmark.
  • Integration tests were scaffolded but not run, so coverage relies on unit tests and manual testing.
